# EX156 시험 대비 정리
### Red Hat Certified Technologist in OpenShift Virtualization

> 기준: OpenShift Container Platform 4.18 / OpenShift Virtualization
> 형식: 단일 섹션, **2시간, 실기형(performance-based)**. 인터넷·반입자료 불가, 단 **제품 documentation은 열람 가능** → 명령어 syntax는 외우기보다 docs 위치를 숙지하는 전략이 유효.

---

## 0. 시험 환경 감 잡기

- 실제 OCP 클러스터에서 VM을 만들고 운영하는 과제를 객관적 기준으로 채점.
- 채점은 **결과물 상태(state)** 기준. 과정이 아니라 "VM이 켜져 있고, 네트워크 붙어 있고, 스냅샷이 존재하는가"를 본다.
- 따라서 작업 후 **반드시 동작 확인**(`oc get vm`, `virtctl`, 콘솔 접속)까지 습관화.
- web console(UI)과 CLI 둘 다 출제 대상이므로 양쪽 흐름을 모두 손에 익혀야 함.

### 필수 사전 명령어 감각
```bash
oc login ...                      # 클러스터 로그인
oc project <namespace>            # 작업 네임스페이스 전환
oc get vm,vmi -A                  # VM / 실행 인스턴스 확인
virtctl version                   # virtctl 사용 가능 여부 확인
```
> `vm` = VirtualMachine(정의), `vmi` = VirtualMachineInstance(실행 중 인스턴스). 이 구분이 트러블슈팅의 기본.

## 1. 가상머신 생성 및 관리 (Create and manage virtual machines)

### 1-1. Web console에서 프로비저닝·관리
- **Virtualization → VirtualMachines → Create** 흐름.
- Template / InstanceType 기반 생성, OS 이미지 선택, CPU·Memory·Disk 지정.
- cloud-init(사용자 계정·SSH key·초기 스크립트) 설정 위치 확인.
- 생성 후 **Start / Stop / Restart / Pause**, 콘솔(Console 탭: Serial / VNC) 접속.
- VM 상세에서 Disks, Network interfaces, Snapshots 탭 위치 숙지.

### 1-2. CLI(virtctl + oc)에서 프로비저닝·관리
```bash
# 생명주기 제어
virtctl start <vm>
virtctl stop <vm>
virtctl restart <vm>
virtctl pause vm <vm>
virtctl unpause vm <vm>

# 접속
virtctl console <vm>      # Serial console
virtctl vnc <vm>          # VNC (그래픽)
virtctl ssh <user>@<vm>   # SSH (설정돼 있을 때)

# 상태 확인
oc get vm <vm> -o yaml
oc describe vm <vm>
oc get vmi <vm>
```

### 1-3. VirtualMachine manifest 핵심 골격
```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: example-vm
spec:
  running: true            # 또는 runStrategy
  template:
    spec:
      domain:
        cpu:
          cores: 2
        memory:
          guest: 2Gi
        devices:
          disks:
            - name: rootdisk
              disk: { bus: virtio }
          interfaces:
            - name: default
              masquerade: {}
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootdisk
          dataVolume:
            name: example-dv
```
> 외워둘 포인트: `domain.devices.disks` ↔ `volumes` 이름 매칭, `domain.devices.interfaces` ↔ `networks` 이름 매칭. 한쪽만 있으면 부팅 실패.

**체크 항목**
- [ ] UI/CLI 양쪽으로 VM 생성 가능
- [ ] start/stop/restart, console/vnc 접속 가능
- [ ] cloud-init으로 계정·SSH key 주입 가능
- [ ] manifest의 disks↔volumes / interfaces↔networks 매칭 이해

## 2. 가상머신 네트워킹 구성 (Configure virtual machine networking)

### 2-1. 사전 정의 네트워크 연결 (user-defined networks 등)
- 기본은 pod network(`masquerade`)로 클러스터 내부 통신.
- 추가 네트워크는 **NetworkAttachmentDefinition(NAD)** 으로 정의 → VM에서 참조.
```bash
oc get network-attachment-definitions
oc get net-attach-def -n <ns>
```
- VM의 `networks`에 `multus: { networkName: <nad> }`, `interfaces`에 해당 이름 추가.

### 2-2. Multihomed VM (다중 인터페이스)
- 한 VM에 여러 인터페이스: pod network + 1개 이상의 추가(secondary) 네트워크.
```yaml
spec:
  template:
    spec:
      domain:
        devices:
          interfaces:
            - name: default
              masquerade: {}
            - name: secondary
              bridge: {}        # 또는 sriov 등
      networks:
        - name: default
          pod: {}
        - name: secondary
          multus:
            networkName: <nad-name>
```
- 부팅 후 게스트 내부에서 `ip a`로 인터페이스 수·주소 확인.

### 2-3. LoadBalancer service로 외부 접근 구성
- VM을 Service로 노출. 빠른 방법:
```bash
virtctl expose vm <vm> \
  --name <svc-name> \
  --type LoadBalancer \
  --port <port> \
  --target-port <vm-port>
```
- 또는 라벨 셀렉터 기반 Service manifest 직접 작성. VM의 pod 라벨과 selector 일치가 핵심.
- LoadBalancer 외부 IP 할당 환경(MetalLB 등) 확인:
```bash
oc get svc <svc-name>
oc get svc <svc-name> -o wide
```

**체크 항목**
- [ ] NAD 조회·참조로 secondary network 연결
- [ ] multihomed VM 구성 후 게스트에서 인터페이스 확인
- [ ] `virtctl expose`로 LoadBalancer Service 생성 및 외부 접근 검증
- [ ] interface type(masquerade/bridge) 차이 이해

## 3. 가상머신 스토리지 관리 (Manage virtual machine storage)

### 3-1. Export된 VM Import
- **DataVolume(DV)** 로 외부 이미지/디스크를 PVC로 가져옴(CDI: Containerized Data Importer).
- import source: URL, registry, blank, PVC clone, upload 등.
```yaml
apiVersion: cdi.kubevirt.io/v1beta1
kind: DataVolume
metadata:
  name: imported-dv
spec:
  source:
    http:
      url: "http://<server>/<image>.qcow2"
  storage:
    resources:
      requests:
        storage: 20Gi
```
- 로컬 파일 업로드 방식:
```bash
virtctl image-upload dv <dv-name> \
  --size=20Gi \
  --image-path=/path/to/disk.qcow2 \
  --insecure
```
- import 진행 상태:
```bash
oc get dv
oc get dv <dv> -o jsonpath='{.status.phase}'   # Succeeded 확인
```

### 3-2. Snapshot 생성·관리
- **VirtualMachineSnapshot** 으로 시점 스냅샷, **VirtualMachineRestore** 로 복원.
```yaml
apiVersion: snapshot.kubevirt.io/v1beta1
kind: VirtualMachineSnapshot
metadata:
  name: snap-1
spec:
  source:
    apiGroup: kubevirt.io
    kind: VirtualMachine
    name: example-vm
```
```bash
oc get vmsnapshot
oc get vmrestore
```
- 복원 시 보통 VM 정지 상태 권장. UI는 VM 상세 → Snapshots 탭에서 Take / Restore.

### 3-3. Clone 생성
- **VirtualMachineClone** CR로 VM 복제(소스 VM → 새 VM).
```yaml
apiVersion: clone.kubevirt.io/v1beta1
kind: VirtualMachineClone
metadata:
  name: clone-job
spec:
  source:
    apiGroup: kubevirt.io
    kind: VirtualMachine
    name: example-vm
  target:
    apiGroup: kubevirt.io
    kind: VirtualMachine
    name: example-vm-clone
```
- PVC/DataVolume 단위 clone(`source.pvc`)도 개념 숙지.

### 3-4. 스토리지 Attach (디스크 추가)
- 실행 중 VM에 디스크 hot-plug:
```bash
virtctl addvolume <vm> --volume-name=<dv-or-pvc>
virtctl removevolume <vm> --volume-name=<dv-or-pvc>
```
- 영구 추가는 manifest의 `volumes` + `domain.devices.disks`에 반영.
- StorageClass / 기본 storage 확인:
```bash
oc get sc
oc get pvc -n <ns>
```

**체크 항목**
- [ ] DataVolume(URL/upload)로 이미지 import 후 phase=Succeeded 확인
- [ ] VirtualMachineSnapshot 생성 → VirtualMachineRestore 복원
- [ ] VirtualMachineClone으로 VM 복제
- [ ] `virtctl addvolume`로 디스크 attach 및 게스트 내 인식 확인

## 5. 시험 전략 메모

1. **docs 활용**: 인터넷은 막혀도 제품 documentation은 열람 가능. snapshot/clone/DataVolume manifest의 정확한 apiVersion은 docs에서 복사하는 게 안전(버전별로 `v1beta1` 등 차이 가능).
2. **작업→검증 루틴 고정**: 모든 과제 후 `oc get`으로 상태 phase/Ready 확인. 채점은 최종 상태 기준.
3. **이름 매칭 오류가 1순위 실수**: disks↔volumes, interfaces↔networks 이름 불일치로 부팅 실패가 잦음.
4. **네임스페이스 확인**: 과제마다 지정 namespace가 다를 수 있음. `oc project` 먼저.
5. **시간 배분**: 2시간 단일 섹션. import/snapshot은 완료까지 시간이 걸리므로 **먼저 트리거**해 두고 다른 과제 진행.
6. **선수 준비**: DO156(Operating Virtual Machines) 실습 환경 + RH124/RH134 수준의 RHEL CLI 감각 권장.
