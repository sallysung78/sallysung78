# 네트워킹 개념정리 (EX156 · 약점 50%)

> VM 네트워킹 + 외부 액세스(Route/LB/NodePort) + UDN. 개념 + **꼭 외울 명령**.
> 핵심 한 줄: **웹=Route / 비웹=LB·NodePort**, **VM 노출=`virtctl expose vm`**.

---

## 0. 🗺️ 네트워크 구조 (계층)
```
┌── OpenShift 클러스터 ─────────────────────────────────────┐
│  ┌ 프로젝트 A (UDN) ┐   ┌ 프로젝트 B (기본) ┐               │
│  │ VM  VM  Pod      │   │ VM  VM  Pod       │              │
│  │  [UDN-A] 격리     │   │  [Pod network] 공용 │            │
│  └──────────────────┘   └───────────────────┘             │
│   가상 네트워크 (OVN-Kubernetes가 구현):                    │
│   ① Pod network(=Cluster network) 클러스터 공용(기본)       │
│   ② UDN  프로젝트 전용(선택, 격리)                          │
│   ③ Service network(172.30.x) ClusterIP·Route·LB용          │
└────────────────────────────────────────────────────────────┘
        ⇣ 위 오버레이가 아래 물리망 위에 얹힘
   [Master Node]═══ Machine network(노드 실제 IP) ═══[Worker Node]
                    API·etcd·kubelet (노드끼리 제어 트래픽)
```
| 네트워크 | 범위 | 역할 |
| --- | --- | --- |
| **Machine network** | 노드(물리) | 노드끼리 통신(API/etcd) |
| **Pod network**(=Cluster) | **클러스터 전체** | 파드/VM 통신(기본, OVN) |
| **UDN** | **프로젝트(NS)** | 격리·서브넷재사용·고정IP(선택) |
| **Service network** | 클러스터 | 서비스 가상IP |

---

## 1. Pod network vs UDN
- **Pod network** = 클러스터 기본 공용. 안 만들어도 모든 VM 자동 연결. (VM은 **masquerade=NAT** 바인딩)
- **UDN**(UserDefinedNetwork) = **프로젝트 전용 격리 네트워크**(선택, 4.18). 안 쓰면 Pod network가 기본.

**UDN 장점 3가지**
| 장점 | 의미 |
| --- | --- |
| 테넌트 격리 | NS마다 격리된 전용 네트워크 (여러 NS 공유=클러스터UDN, 관리자권한) |
| 일관된 IP | 여러 NS가 **같은 서브넷 재사용**해도 격리 (개발/테스트/운영) |
| **영구 IP** | VM 고정 IP, 재시작·노드이동에도 유지, **L2라 NAT 없이 마이그레이션** |
> 💡 VM에 중요 = ③ 영구 IP + NAT 없는 마이그레이션(다운타임↓).

---

## 2. VM 네트워크 바인딩 (primary / secondary)
```
VM
 ├ eth0 (primary, 필수 1개): Pod network→masquerade(기본) 또는 UDN
 └ eth1.. (secondary, 선택): 2차 네트워크 = Multus + NAD
```
**2차 네트워크(NAD/Multus) 종류**: Linux bridge / OVN localnet·layer2 / SR-IOV
```yaml
# VM에 2차 NIC 붙이기 (개념)
spec:
  template:
    spec:
      domain:
        devices:
          interfaces:
          - name: default
            masquerade: {}        # 파드 네트워크
          - name: bridge-net
            bridge: {}            # 2차
      networks:
      - name: default
        pod: {}
      - name: bridge-net
        multus: { networkName: my-bridge-nad }   # NAD 이름
```
> 체크: interface name ↔ network name **짝 맞아야**. masquerade는 파드 네트워크만.
> 🔴 **2차 NIC 추가 후 재부팅**(SNO는 특히). 호스트 브리지 구성은 **NMState(NNCP)**.

## 3. 🌐 외부 액세스 서비스 4종 ⭐
| 유형 | 트래픽 | 특징 |
| --- | --- | --- |
| **NodePort** | HTTP/non-HTTP | 모든 노드 포트 열림(보안 위험) |
| **LoadBalancer** | HTTP/non-HTTP | 외부 IP. 클라우드 LB / 온프렘=**MetalLB** |
| **Ingress** | HTTP/HTTPS/TLS(SNI) | k8s 표준 |
| **Route** ⭐ | HTTP/HTTPS/TLS | **OpenShift 전용**, 고유 hostname |
> 🔑 **웹(HTTP/S)=Route / 비웹(UDP·일반TCP)=LoadBalancer·NodePort.**

## 4. Route (경로)
- **전제: ClusterIP 서비스 먼저** → `oc expose service`로 Route 생성.
- **DNS 자동**: `routename-namespace.기본도메인` (예: intranet-prod.apps.mycompany.com)
- **구현**: HAProxy 라우터 포드. 와일드카드 DNS → 라우터 IP.
```bash
oc expose service/web                          # 기본(이름=web, DNS 자동)
oc expose service/web --name web --hostname web-production.apps.mycompany.com
oc get route web                               # HOST 확인
# 경로 기반(path): 같은 hostname, URL 경로로 분기
oc expose service/static --path=/static --hostname=intranet-prod.apps.mycompany.com
```
콘솔: Networking → Routes → Create Route.

## 5. 🔒 암호화 Route — TLS 종료 3종 ⭐
| 종류 | TLS 종료 위치 | 라우터→백엔드 | 인증서 |
| --- | --- | --- | --- |
| **edge** | 라우터에서 | 암호화 **안 됨** | 라우터 제공 |
| **passthrough** | 종료 안 함(그대로) | 암호화됨 | **앱이** 제공 |
| **reencrypt** | 라우터 종료 후 재암호화 | **암호화됨(전구간)** | 라우터+백엔드 |
```bash
# oc expose = 평문(HTTP)만! 암호화는 oc create route
oc create route edge --service web --hostname api.apps.acme.com   # edge|passthrough|reencrypt
#   사용자 인증서: --key, --cert
```
**Insecure traffic 정책**: None(차단) / Allow(HTTP 허용) / Redirect(HTTP→HTTPS).

## 6. ⭐⭐ VM 노출 = `virtctl expose vm` (계속 나옴! 무조건 외우기)
> VM은 `virtctl expose`가 간편 — **라벨 추가·재시작 불필요** (자동 `vm.kubevirt.io/name` 라벨 사용).

```bash
# ① VM 서비스 생성 (자주 나오는 그 명령)
virtctl expose vm hello-web --name=hello-web --type=ClusterIP --port=80 --target-port=80
# ② Route 생성 (웹이면)
oc expose service/hello-web --name=<route이름>
```
| 플래그 | 의미 |
| --- | --- |
| `--name` | 만들 서비스 이름 |
| `--type` | ClusterIP / NodePort / LoadBalancer |
| `--port` | 서비스가 받는 포트 |
| `--target-port` | VM 안 실제 포트 (생략=`--port`와 동일) |

> 수동 방식(VM에 라벨 → 재시작 → Service YAML selector)은 **virtctl expose가 대신**해줌 → 개념만.
> 앱 기본 포트: 웹 80 / HTTPS 443 / SSH 22 / RDP 3389.

**LoadBalancer 노출 + 검증**
```bash
virtctl expose vm <vm> --name=<svc> --type=LoadBalancer --port=80
oc get svc <svc>                                              # EXTERNAL-IP (pending이면 LB/MetalLB 없음)
oc get svc <svc> -o jsonpath='{.status.loadBalancer.ingress[0].ip}'
curl http://<EXTERNAL-IP>:80
```

## 7. Route vs Ingress
| | **Route** | **Ingress** |
| --- | --- | --- |
| 소속 | OpenShift 전용 | k8s 표준 |
| 기능 | TLS 재암호화·passthrough·트래픽분할 多 | 일부 없음(재암호화 X) |
| 관계 | — | OpenShift는 **Ingress를 Route로 구현** |

## 8. ⚖️ LoadBalancer + MetalLB (non-HTTP 노출) ⭐

### 왜 LB/NodePort? (Route로 안 되는 것)
> **Route/Ingress = HTTP/HTTPS/TLS만.** SSH·DB(MySQL)·SMTP·POP3·IMAP·LDAP 등 **non-HTTP는 Route 불가** → **NodePort 또는 LoadBalancer** 사용.

### NodePort vs LoadBalancer
| | **NodePort** | **LoadBalancer** ⭐ |
| --- | --- | --- |
| 노출 | 모든 노드의 포트(**30000~32767**) | **고정 외부 IP** + 포트 |
| 노드 이동 시 | 노드 IP 노출 필요(보안↓), 클라우드선 IP 비영구 | **VM이 노드 옮겨도 IP 안 바뀜** |
| 권장 | 비권장 | 권장 |
> NodePort `nodePort:` 생략 시 자동 할당. 범위 밖 포트 X.

### MetalLB Operator (온프렘/베어메탈 LB)
> 클라우드 아닌 클러스터(베어메탈·SNO)는 클라우드 LB가 없음 → **MetalLB**가 LB 서비스에 외부 IP 할당.
- **모드 2종**: **L2(ARP, 기본)** = ARP로 IP 광고, 한 노드로 트래픽 / **L3(BGP)** = BGP 경로 광고, AS 번호 필요.
- 설치 = OLM, **`metallb-system`** 프로젝트. **CR 3종** (관리자가 구성):
  | CR | 역할 |
  | --- | --- |
  | **MetalLB** | 기본 인스턴스 |
  | **IPAddressPool** | LB에 줄 **IP 범위** (예: 192.168.50.20-40) |
  | **L2Advertisement** | 그 풀을 **L2(ARP)로 광고** |
```bash
oc get metallb,ipaddresspool,l2advertisement -n metallb-system
```

### VM을 LoadBalancer로 노출 (핵심)
```bash
virtctl expose vm vm1 --name=vm1-ssh --type=LoadBalancer --port=22 --target-port=22
```
- selector = **`vm.kubevirt.io/name: vm1`** (virt-launcher 포드 표준 라벨, 자동)
- **검증 순서**:
```bash
oc get svc                # EXTERNAL-IP 떴나 (MetalLB가 할당, 예 192.168.50.23)
oc get endpoints          # virt-launcher 포드 IP:포트로 확인됐나 (<none>이면 selector 불일치)
oc get vmi                # VMI IP/노드 확인
nc -vz <EXTERNAL-IP> 22   # TCP 연결 확인
ssh developer@<EXTERNAL-IP>   # 실제 접속
```

### 여러 포트 노출
- `virtctl expose`는 **`--port` 하나만** 가능. 여러 포트는 **YAML 편집**(각 포트에 **`name` 필요**).
- virtctl은 `--port-name`으로 포트 이름 지정 / 기존 서비스는 `oc edit service <svc>`.

### 콘솔: SSH over LoadBalancer
```
VM → Configuration → SSH 탭 → SSH service type = "SSH over LoadBalancer"
```
> ⚠️ 활성화 직후 **endpoint가 `<none>`**(selector 불일치)일 수 있음 → **라이브 마이그레이션**(Actions → Migration → Compute)하면 라벨 맞는 새 virt-launcher 생성 → endpoint 확인됨.
> (사전조건: Overview → Settings → SSH configuration에서 "SSH over LoadBalancer" 활성).

## ⭐ 무조건 외울 명령 (네트워킹)
```bash
# VM 서비스 노출 (제일 자주!)
virtctl expose vm <vm> --name=<svc> --type=ClusterIP --port=80 --target-port=80
# Route 생성 (웹)
oc expose service/<svc> --name=<route>              # 평문
oc create route edge --service <svc> --hostname <host>   # 암호화(edge|passthrough|reencrypt)
# 외부 IP(LB) — non-HTTP(SSH/DB 등)
virtctl expose vm <vm> --name=<svc> --type=LoadBalancer --port=22 --target-port=22
oc get svc                 # EXTERNAL-IP 확인
oc get endpoints           # virt-launcher IP:포트 확인(<none>=selector 불일치)
nc -vz <EXTERNAL-IP> 22    # TCP 연결 검증
oc get svc,route,nad,endpoints
oc get metallb,ipaddresspool,l2advertisement -n metallb-system   # MetalLB 확인
```
> 까먹으면: `virtctl expose --help` / `oc expose --help` / `oc create route --help`
